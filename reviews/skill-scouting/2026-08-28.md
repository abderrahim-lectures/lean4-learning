# Skill scouting — 2026-08-28

## Summary

One genuinely new, concretely applicable pattern turned up: dedicated Lean
4/Mathlib skill packs (`leanprover/skills`, `cameronfreer/lean4-skills`)
that add an explicit **axiom-checking step** and **mathlib semantic search
(LeanSearch/Loogle)** as part of their proof workflow, neither of which
`lean-code-auditor` currently does. Everything else found in this pass was
generic Claude Code skill-marketing content already reflected in this
repo's existing skills.

## Findings

### 1. Explicit `#print axioms` check after every proof

- Source: https://github.com/cameronfreer/lean4-skills (fetched via
  WebFetch; the pack's `lean-proof` checkpoint workflow is described as
  "per-file + project build, axiom check, commit").
- Pattern: after a proof block builds, run Lean's `#print axioms
  <theorem_name>` and confirm the axiom list is limited to the expected
  set (`propext`, `Classical.choice`, `Quot.sound`) with nothing
  unexpected (no stray `sorryAx`, no ad hoc axiom). This catches proofs
  that compile but are silently unsound or incomplete (e.g. `sorry`
  hidden behind a tactic that suppresses the warning, or an accidental
  `axiom` declaration) in a way `lake build` output alone does not always
  surface loudly.
- Concrete proposal: add a step to `.claude/skills/lean-code-auditor/SKILL.md`'s
  build-verification section: after `lake build` succeeds for a chapter's
  snippet, also run `#print axioms <name>` (via a scratch file invoking
  `lake env lean`) for each top-level theorem/def introduced in that
  snippet, and flag any axiom beyond the three standard ones as a finding
  requiring the same WHAT/WHY/IMPACT/FIX treatment as a build failure.

### 2. Mathlib semantic search as a required step before accepting a hand proof

- Source: https://github.com/leanprover/skills (fetched via WebFetch) and
  corroborated by the arXiv description of `lean-lsp-mcp` retrieved via
  WebSearch (search tools "to find relevant lemmas" wired into a
  Lean-focused agent).
- Pattern: before signing off on a bespoke tactic proof in a review, query
  LeanSearch or Loogle for an existing Mathlib lemma with the same
  statement shape; flag hand-rolled proofs that duplicate library results
  as a style/maintainability finding, not just correctness.
- Concrete proposal: `lean-code-auditor` currently checks "does it
  compile, does it match the prose, does it fake a proof" but has no step
  for "does Mathlib already have this." Add a check that, for any
  non-trivial proof (more than ~3 tactic lines) of a standard-looking
  algebraic fact, the reviewer searches Mathlib (via `exact?`/`apply?` in
  the Lean project, or loogle.lean-lang.org) before accepting the
  hand-written proof as pedagogically necessary rather than redundant.
