\begin{learningobjectives}
\begin{itemize}
\tightlist
\item
  Read the type of a Lean term with \texttt{\#check} and distinguish \texttt{\#check} from \texttt{\#eval}.
\item
  Write basic \texttt{def}s with implicit arguments.
\item
  Understand what makes a type \emph{dependent} (via \texttt{Fin}/\texttt{Vec}).
\end{itemize}
\end{learningobjectives}


Every section below answers one question, and each question is forced by the answer to the one before it. It helps to see the whole chain before working through it line by line.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{What is a type, and why does Lean check it before running anything?} (\hyperref[sec:01-basics:01-everything-has-a-type:1]{Section 1}) Ordinary languages catch type errors, if at all, at the moment the bad line runs, possibly months after it shipped, on a rarely-hit branch. Lean checks the question ``what kind of thing is this?'' once, by reading the expression, for every possible input at once. That single idea, that \texttt{\#check} gives a static guarantee while \texttt{\#eval} gives a one-off fact, is the foundation everything else in this book stands on.
\item
  \textbf{Given that types are checked this strictly, how are new ones built, and how does Lean avoid forcing tedious repetition at every call site?} (\hyperref[sec:01-basics:02-def-let-implicit:1]{Section 2}) \texttt{def} and \texttt{let} are the two ways to name a term. Implicit arguments (\texttt{\{α : Type\}}) are how a single definition like \texttt{identity} serves \emph{every} type at once without being rewritten per type. Nothing here is new machinery yet, just the vocabulary needed to read and write ordinary Lean definitions fluently.
\item
  \textbf{Is a type always fixed in advance, the way \texttt{Nat → Nat} never changes its output type?} (\hyperref[sec:01-basics:03-dependent-types:1]{Section 3}) No, and this is the single feature that separates a proof assistant from an ordinary typed language. A type can depend on a \emph{value}, not just another type. \texttt{Fin n} is a different type for each \texttt{n}. The \emph{return type} of a function can change depending on which argument it receives. This is what finally lets a signature say ``these two lists must have the same length'' and have Lean enforce it, rather than merely hope for it.
\end{enumerate}

That single feature, a type depending on a value, is the hook the next chapter picks up directly. \texttt{Fin}/\texttt{Vec} are dependent types encountered concretely here; naming the vocabulary behind them precisely, and the formal system they are instances of, is the job of \hyperref[sec:02-terminology-and-coc:00-index:1]{Chapter 2}, not of this chapter.
