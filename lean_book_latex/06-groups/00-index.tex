\chapter{\texorpdfstring{Chapter 6: Structures and classes --- defining a \texttt{Group}}{Chapter 6: Structures and classes --- defining a Group}}\label{sec:06-groups:00-index:1}

Chapter 5's checkpoint project already built a \texttt{Monoid} --- data plus proof obligations, bundled in a \texttt{structure}, using nothing but Chapters 1--5. Each section below asks the next question that answer forces:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{A monoid has an associative operation and an identity --- what is missing to reach the structures Part II is actually about?} (\hyperref[sec:06-groups:01-definition:1]{Section 1}) One axiom: every element must be invertible. Adding it to the monoid's data turns ``a set with an associative operation'' into a \textbf{group}, stated first in ordinary mathematical notation before any Lean is written.
\item
  \textbf{How does that mathematical definition become an actual Lean type?} (\hyperref[sec:06-groups:02-translating:1]{Section 2}) Field by field: first the raw data (\texttt{GroupData}, no axioms), then the same data with one proof-obligation field added per axiom (\texttt{Group}). This is the general recipe used throughout the book, applied here for the first time to something with this many moving parts.
\item
  \textbf{Is the definition non-vacuous --- does anything actually satisfy it?} (\hyperref[sec:06-groups:03-integers-example:1]{Section 3}) Yes: \((\mathbb{Z}, +, 0, -)\), assembled as \texttt{intGroup} by citing one core-library lemma per axiom. But \texttt{intGroup} is abelian, so it never distinguishes a left inverse from a right one.
\item
  \textbf{Does that abelian example secretly rely on commutativity somewhere \texttt{Group}'s definition does not require it to?} (\hyperref[sec:06-groups:04-permutations-example:1]{Section 4}) Building a genuinely non-abelian group --- the permutations of three elements --- forces every axiom to be checked honestly, left and right separately, and answers the question directly: no, nothing in \texttt{Group} assumes commutativity.
\item
  \textbf{Now that two concrete groups exist, how is their data actually used?} (\hyperref[sec:06-groups:05-accessing-fields:1]{Section 5}) The same way any structure's fields are used, from Chapter 2 onward: ordinary projection, whether the field holds data or a proof.
\item
  \textbf{Two groups have now been built by hand, field by field --- is that effort about to be paid back?} (\hyperref[sec:06-groups:06-why-bundle:1]{Section 6}) Yes: any theorem proved once about an arbitrary \texttt{Group G} applies automatically to \texttt{intGroup}, to the permutation group, and to every group built afterward. Chapter 7 is that payoff, carried out in full.
\end{enumerate}

By the end of the chapter, \texttt{Group} is no longer just a definition sitting on the page --- it is a structure with two concrete inhabitants, one commutative and one not, and a stated reason to keep building on it.
